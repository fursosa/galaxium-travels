# Architecture — Galaxium Travels

This document explains the key architectural decisions in Galaxium Travels: why the system is split the way it is, why certain patterns look unusual, and what trade-offs were made deliberately.

---

                                       │

### Why three services?

The three-service split exists to create realistic complexity for demonstrating AI agent challenges:

1. **Python backend** — owns the core booking database. It's the authoritative source for `users`, `flights`, and `bookings`.
2. **Java hold service** — owns the transient hold lifecycle. It's a separate deployment that speaks a different language, has its own database (`holds.db`), and communicates back to Python over HTTP.
3. **React frontend** — a standard browser client that talks exclusively to the Python backend. It never calls the Java service directly; all Java calls go through Python proxy endpoints.

## MCP dual-API pattern

Every operation in the Python backend is accessible two ways:

```
POST /book  (REST, used by frontend + curl)
      │
      ▼ same function
   book_flight_endpoint()
      │
      ▼
   booking.book_flight()  ← pure service function, no HTTP

FastApiMCP wraps the FastAPI app at startup and auto-generates
MCP tools from every route.
```

`FastApiMCP` (from `fastapi_mcp`) introspects the FastAPI route registry and generates MCP tool definitions at mount time. This means:

- **You never write MCP tool handlers manually** — the REST route definition is the single source of truth.
- **Tool names match endpoint function names** — `book_flight_endpoint` → MCP tool `book_flight_endpoint`.
- **Docstrings become tool descriptions** — keep them clear and precise.

### Critical instantiation order

```python
# server.py — this order is mandatory

app = FastAPI(...)          # 1. FastAPI app first

# ... register all routes ...

mcp = FastApiMCP(app)       # 2. MCP wraps app AFTER routes are registered
mcp.mount_http()            # 3. Mount MCP at /mcp
```

Swapping steps 1 and 2 breaks lifespan composition and the MCP server won't see any routes.

## Database session management

There are two session patterns in the codebase and they must not be mixed:

### Pattern A — FastAPI dependency injection (REST endpoints)

```python
@app.post("/book", response_model=BookingOut)
def book_flight_endpoint(request: BookingRequest, db: Session = Depends(get_db)):
    result = booking.book_flight(db, ...)
    ...
```

`Depends(get_db)` is FastAPI's dependency injection. `get_db()` opens a session, yields it, and closes it in a `finally` block when the request completes.

### Pattern B — Direct session management (MCP tools, seed.py)

```python
# In seed.py or any code that runs outside of a FastAPI request context
db = SessionLocal()
try:
    # ... do work ...
    db.commit()
finally:
    db.close()
```

**MCP tools cannot use `Depends(get_db)`** because they aren't invoked through the FastAPI request pipeline. They must use Pattern B.

### Testing implication

Because `SessionLocal` is used in two places (`db.py` and implicitly via `server.py`), tests must patch it in both:

```python
# conftest.py — both patches are required
monkeypatch.setattr("db.SessionLocal", TestingSessionLocal)
monkeypatch.setattr("server.SessionLocal", TestingSessionLocal)
```

Patching only one leaves the other path hitting the real `booking.db` file.

## Service function error handling

Service functions (in `services/`) return a Union type, not exceptions:

```python
def book_flight(
    db: Session, user_id: int, name: str, flight_id: int, seat_class: SeatClass
) -> BookingOut | ErrorResponse:
    ...
```

**Why Union types instead of exceptions?**

- MCP tools receive service results and need to report failures as structured data, not Python exceptions.
- It makes the success/failure branching explicit at every call site.
- Error codes (`USER_NOT_FOUND`, `NAME_MISMATCH`, etc.) give callers — including AI agents — precise information to act on.

The REST layer translates `ErrorResponse` to HTTP status:

```python
if isinstance(result, ErrorResponse):
    status = 404 if result.error_code in ("FLIGHT_NOT_FOUND", "USER_NOT_FOUND") else 409
    raise HTTPException(status_code=status, detail=result.model_dump())
```

## The proxy error swallow

The Java proxy endpoints catch `httpx.HTTPError` and return `{"error": "..."}` with **HTTP 200**:

```python
@app.post("/quotes", tags=["Quotes"])
async def create_quote(quote_data: dict):
    async with httpx.AsyncClient() as client:
        try:
            response = await client.post(...)
            response.raise_for_status()
            return response.json()
        except httpx.HTTPError as e:
            return {"error": f"Failed to create quote: {e!s}"}  # ← HTTP 200!
```

**Why HTTP 200 on error?**

This was a deliberate demo design choice to create a realistic pitfall — the kind of thing that exists in real enterprise systems where a "gateway" layer hides downstream errors from upstream status code checks.

**How to handle it correctly:**

```typescript
// api.ts — assertNotProxyError must be called on every quote/hold response
const assertNotProxyError = (data: unknown): void => {
  if (data && typeof data === 'object' && 'error' in data) {
    throw new Error((data as { error: string }).error);
  }
};

export const createQuote = async (data: CreateQuoteRequest): Promise<Quote> => {
  const response = await api.post('/quotes', data);
  assertNotProxyError(response.data);   // ← explicit check required
  return response.data as Quote;
};
```

## Name-match booking security

`book_flight()` validates both `user_id` and `name`:

```python
user = db.query(User).filter(
    User.user_id == user_id,
    User.name == name         # both conditions required
).first()
```

This is an intentional non-standard pattern. The rationale: in this demo the user presents their name as part of the booking request (like showing a passport), and the system verifies it matches the account. A `NAME_MISMATCH` error is returned if a valid `user_id` is submitted with the wrong name.

## Hold lifecycle state machine

```
         createQuote()
              │
              ▼
           CREATED  ──(expires)──► (discarded, no state)
              │
         createHold()
              │
              ▼
            HELD  ──────(auto-expires after 15 min)──► EXPIRED
              │
     ┌────────┴────────┐
confirmHold()      releaseHold()
     │                  │
     ▼                  ▼
 CONFIRMED           RELEASED
     │
  (Java calls)
     │
     ▼
 Python creates
 real Booking
```

The Java `HoldExpirationScheduler` runs every 60 seconds and transitions `HELD` holds whose `reservedUntil` is in the past to `EXPIRED`.

## Frontend state management

User identity is managed via React Context + localStorage:

```
UserProvider (useUser.tsx)
  └── UserContext
        ├── user: User | null
        ├── setUser(user)     ← also writes to localStorage
        └── logout()          ← clears localStorage

Key: "galaxium_user"
```

Active holds (created but not yet confirmed) are stored in localStorage via `holdStorage.ts` so they survive page refreshes and appear in the My Bookings view.

## Database choices

| Environment | Database | Why |
|---|---|---|
| Local dev | SQLite (`booking.db`) | No setup required; `booking.db` and `holds.db` are committed |
| Docker Compose | PostgreSQL | Closer to production; configured via `DATABASE_URL` env var |
| AWS ECS | SQLite | `DATABASE_URL` intentionally unset; data is ephemeral per task |
| IBM Code Engine | PostgreSQL | Set via Code Engine environment secrets |

The SQLite files are committed to the repo. They're regenerated at startup when non-empty (the seed function short-circuits if `users` has rows), so they serve as a fallback seed baseline.
